## BLOCKING CHALLENGES

### B-1 — "4D falls out additively" is asserted in three syntheses and supported by ZERO of them. (BLOCKING)
S2 §3.2: *"4D falls out additively: a temporal source is 'just' a source whose covering-tile/cache key includes a time coordinate."* S5 §3 and S6 §3 repeat the same "additive source dimension" claim. **Every one of these traces to B3/B5 INFERENCE that the source files themselves flag as unsupported.** S5 §5.3 admits it outright: *"4D/temporal is under-specified by every source… I cannot validate the roadmap against the 4D goal."* A6 ε is the only first-hand finding and it says the opposite of "additive": there is **no temporal data dimension at all** — `TimeStop<T>` is a paint-interpolation stop, and grep for `valid_time|epoch|datetime` finds nothing in the data path. Adding a time coordinate to the tile cache key is not additive; it multiplies the working set (N timesteps × the tiles already overflowing the 256-tile GPU cap — see B-3), forces temporal interpolation/morphing in the vertex path, and requires a time axis on `ShowCommand` that does not exist. Calling this "additive" is the textbook trivialization.
- **MUST:** Either delete the "4D is additive" claim from S2/S5/S6, or produce a concrete 4D spike: what `ShowCommand`/tile-key/vertex-buffer changes a `valid_time` interval requires, and what it does to the GPU working-set budget. You cannot endorse a "5-year / 4D" roadmap while conceding (S5 §5.3) you can't evaluate it against 4D. Pick one.

### B-2 — The GPU-CI golden-master keystone is recommended to gate exactly the surface it is PROVEN blind to. (BLOCKING — internal incoherence)
Every synthesis makes "stand up GPU-CI + promote the matrix to a golden-master gate" the load-bearing first move (S4 R1, S5 R3, S6 Phase 0, S1 R3's risk note). And every synthesis cites A5 §4.5: flat fills render 56.75% but the **same geometry extruded renders 0.00%** under SwiftShader. S6 Phase 4 even admits S20 "is only safe once Phase 0 includes an extrusion cell." **But the matrix has no extrusion oracle to add.** I read `matrix-oracles.ts`: the oracle kinds are `ink_family`, `disc_fraction`, and perceptual pixel-diff — all 2D coverage/presence checks. None inspects depth ordering, wall geometry, silhouette, or height. So "add an extrusion cell" is not a config line; it requires inventing a 3D-correctness oracle that does not exist anywhere in the repo, on a real-GPU runner whose feasibility is itself unproven (every S-file flags this as the #1 open risk). The keystone that supposedly de-risks the headline decomposition (S20) cannot see the headline decomposition's failure mode, AND the gate runs on infrastructure nobody has confirmed exists.
- **MUST:** Concede that Phase 0 is two unbuilt things, not one: (a) a procurable real-GPU runner [feasibility unknown], and (b) a **new 3D/depth/extrusion oracle** [does not exist, non-trivial to design — "is this frame correct?" for a 3D scene has no `disc_fraction` analogue]. Cost and sequence (b) explicitly. Until (b) exists, S20/Phase-4 is NOT unblocked by "GPU-CI" — that is hand-waving.

### B-3 — A whole failure mode — GPU-tile-cache thrash under massive/3D data — is declared "out of scope" by S3 and missed by all others, yet it is verifiable and live. (BLOCKING — missed subsystem)
S3 §5.5 says the cache-thrash concern (visible set > cache cap → re-upload every frame) is *"explicitly out of A3's scope… I cannot confirm or deny it."* It is trivially confirmable and I confirmed it: `MAX_GPU_TILES_DESKTOP=256` (`debug/AGENTS.md`, `arena-eviction-policy.test.ts:95`) while globe visibility allows `MAX_TILES=300` (`globe.ts:422`), and the FLICKER logs in `tile-pipeline-predictor.test.ts` show real sessions at `gpuCache=315/375` — i.e. **the visible set already exceeds the GPU cache cap today**, forcing re-upload churn (a CPU↔GPU bandwidth/thermal problem, not a leak). This is the single most goal-relevant axis: "massive data" and "3D-tiles" (larger, hierarchical payloads — B5 §e) make the working set *bigger*, so a 256-tile byte cap that already overflows is the thing that breaks first under the stated goal. S3 scored memory "3/5 and rising" while waving off the one churn axis that the 5-year goal stresses hardest.
- **MUST:** Promote cache-thrash from "unverifiable" to a sized finding. State whether the 256-tile desktop cap survives 3D-tiles/4D working sets, or whether the eviction/cap policy must become screen-coverage-aware. This is a forward-capacity question the reckoning currently does not answer.

### B-4 — The recommended deck.gl/MapLibre rendering contract is endorsed without testing it against X-GIS's actual constraints; the "limited transfer" caveats are buried. (BLOCKING — overclaiming a target)
S5 §3 and S6 §3 hold up deck.gl's "layer = cheap descriptor, recompute-and-diff, persistent GPU state moved forward" and `finalizeState` as the target rendering contract. B4 itself flags three places this *does not* transfer for X-GIS: (i) the reactive recompute model "assumes shallow-compare-friendly props" and X-GIS's **large binary tile buffers** must use the escape hatch or it over/under-invalidates (B4 §3 "Where transfer is limited"); (ii) deck.gl "assumes a host owns camera/projection" — X-GIS owns its own ECEF/projection pipeline, so the geo-layer machinery is off-limits; (iii) per B3 §3 (cited only in S1 §5.3) **WebGPU GPUBuffer creation cannot happen in a worker** without a per-worker device, so the clean "Bucket builds the buffer" split does NOT transfer 1:1 — X-GIS must keep worker=CPU-typed-array, main=writeBuffer. S2 §5.4 mentions caveat (i) in passing; none of the synthesis *recommendations* are conditioned on these. S6 §3 states the deck.gl model as "the destination" flatly. A target architecture that imports a sibling's model while burying the three places that sibling's model breaks on your terrain is overclaiming.
- **MUST:** Re-state the rendering-contract target with the binary-buffer escape hatch and the worker/GPU-creation boundary as first-class constraints, not uncertainties. Specifically: does the "persistent GPU state moved forward on diff" model survive when the diffed unit is a 192-byte-stride packed tile buffer, not a shallow-comparable prop bag? If not, say what the actual target is.

### B-5 — The reckoning never reconciles the two competing remediation plans; S6 flags it and then sequences around it anyway. (BLOCKING — internal inconsistency the owner will hit immediately)
A5 §3.3 and S6 §5 both record that the repo has a **second** remediation plan (the 06-08 rendering audit) that re-prioritizes toward **reversed-Z depth + RTC f64-matrix precision** as "Tier 1" — work that is *not in* the S0–S20 sequence at all. The live task list confirms this is active, not hypothetical: task #8 "desktop-gated rendering (#4 reversed-Z)", task #9 "decide OIT fate". S6 §5 admits: *"I cannot adjudicate this from A\* alone… if depth-precision is causing live correctness bugs it may belong before Phase 4."* So the synthesis sequences six phases around the S19/S20 roadmap while conceding a depth/precision/OIT track might preempt the whole ordering — and **no S-file analyzes depth precision or OIT compositing at all**, despite OIT being a named open task and depth being the substrate every 3D/extrusion/3D-tiles frame depends on. For a 3D-forward goal, ignoring depth-buffer architecture and order-independent transparency is not a minor omission.
- **MUST:** Adjudicate. Either fold reversed-Z/RTC-precision/OIT into the sequence with an explicit rank, or state on the record why depth/compositing correctness is *not* a prerequisite for 3D-tiles/4D. A reckoning that can't say whether depth-precision precedes its headline phase has not actually sequenced the work.

## MAJOR CHALLENGES

### M-1 — The syntheses inherit A6's CRITICAL packaging blocker and then bury it. (MAJOR — priority inversion)
A6 AXIS α is unambiguous: the library **cannot be `npm install`ed** (`workspace:*` → `private:true` → `main: ./src/index.ts` raw TS chain), and ranks it CRITICAL / "blocks everything downstream." This is the only finding in the entire corpus that makes the stated end-goal ("sellable library") literally impossible *today*, independent of any architecture work. Yet S1–S4 do not mention it; only S6 §3 lists it among "installable/observable/extensible" and S5 R6 bundles it loosely. None puts it in the critical path. You can have a perfect subsystem taxonomy and still ship nothing because the dist is unresolvable. Prioritizing god-file decomposition (multi-month, high-risk) over a packaging fix (days, zero render risk) is a priority inversion for anyone who actually wants to ship.
- **MUST:** Place AXIS α in the sequence explicitly — it is the cheapest CRITICAL and gates the goal more directly than S20. Concede that "5-year sustainability" is moot if v0 can't be installed.

### M-2 — Device-loss-is-terminal and no `'error'` event are A6 CRITICALs that the render-path-centric thesis structurally cannot see. (MAJOR — S4 half-concedes, others miss)
A6 E1: device loss → `deviceLost=true` → render loop halts with **no recovery path** anywhere (`requestDevice` called once at init, `gpu.ts:140/177/195`). A6 E2: no `'error'` event exists. S4 §5.1 honestly flags that the "behavioral safety net" thesis does NOT cover the contract/event/lifecycle class and that this needs "a co-equal type/contract net." That concession is correct — and it quietly guts the unifying thesis of S4/S6 ("build ONE net first and everything unlocks"). For a *desktop* app under heavy GPU load (the owner's explicit worry), a terminal device-loss is arguably the highest-severity runtime failure in the whole reckoning, and it is a side-note. Massive data + 3D-tiles + 4D = more GPU pressure = more device-loss events; a renderer that dies permanently on the first driver reset is not 5-year-viable regardless of how clean its god-files are.
- **MUST:** Elevate E1 (device-loss recovery loop per the WebGPU spec) and E2 (`'error'` event) to first-class sequence items, and stop implying the visual safety-net is "THE" net. There are two nets; the thesis (S4 §1, S6 §1) overstates by saying there is one.

### M-3 — "Reject ECS, keep DOD hot path + OOP control plane" is asserted as settled, but the evidence to settle it for a 4D-city does not exist. (MAJOR — under-examined for the actual goal)
S1 §3.6, S2 §3, S5 §3, S6 §3 all repeat B5's "reject a general ECS; X-GIS's spatial data is ECS's documented weak spot." That is correct *for the tile/raster core*. But B5 §a (and S1 §5.4, honestly) carve out that a *scoped* ECS may be warranted "if the 4D-city scene introduces genuinely many heterogeneous dynamic objects" — and **none of A1/A5/A6 contains any evidence about the 4D scene-graph's object heterogeneity** because that subsystem does not exist yet. So five syntheses state "reject ECS" as a target-state decision while the one workload that would justify reconsidering it (animated, heterogeneous city objects over time) is exactly the unbuilt thing. This is solving the present (tile renderer) and stamping the answer onto the future (city scene-graph) without looking.
- **MUST:** Scope the ECS rejection to the tile/raster core explicitly, and mark the 4D dynamic-object scene-graph as an open design question with its own Rule-of-Three gate — do not let "reject ECS" read as a verdict on a subsystem nobody has specified.

### M-4 — "Route every mutation (incl. the gesture lane) through one `_update()` funnel" is recommended without resolving the per-event cost, on a path the syntheses admit is unmeasured. (MAJOR — possible re-introduction of the perf debt the owner hates)
S2 R1 and S3 R5 make the single-funnel the keystone state fix. S2 §5.2 then admits: *"neither A2 nor B3 measures the per-gesture-event cost of op-dispatch on a high-frequency drag/pinch stream… if op-logging every pointer delta is too expensive, the funnel may need a fast-path."* Recommending the keystone while conceding you don't know if it's affordable on the hottest input path (pointer-move at device rate) is exactly the "introduce overhead, discover it later" pattern. MEMORY already records adaptive-DPR dead code and label-pipeline as the dominant CPU hot path; adding op-dispatch + bitset bookkeeping per pointer delta could regress drag latency the owner has repeatedly fixed.
- **MUST:** Make the funnel recommendation conditional on a measured fast-path (tag-domain-without-recording-op for high-frequency gestures), or down-rank it below a measurement spike. Do not present an unmeasured hot-path change as the keystone.

### M-5 — The plugin/extensibility axis (3D-tiles entry point) is the most goal-critical structural gap and it is treated as a corollary of S20, not a designed subsystem. (MAJOR — the actual 3D-tiles question)
A6 β: there is **no registration surface** (`registerLayer|registerSource|CustomLayer` → nothing); "to add 3D-tiles today you fork the engine." S5 R6 and S6 §3 both lean on A6's own framing that "β is the same wound as S20." That framing is convenient and probably wrong as stated: S20 is an *internal* eval→draw seam; a plugin API is an *external contract* with versioning, lifecycle, sandboxing, and a stable type surface (which A6 γ shows is exactly where X-GIS erases types — `{ast:unknown}`, `as unknown as` ×354). Building the eval→draw seam does not automatically yield a publishable extension point; conflating them lets the reckoning claim 3D-tiles is addressed when only the internal half is. B2 §5 (registration-over-reference) is the real model and it is a distinct design effort.
- **MUST:** Separate β (external plugin/registration contract for 3D-tiles/glTF/point-cloud) from S20 (internal seam). Concede they are related but not identical, and that the 3D-tiles entry point needs its own typed, versioned registration design — the single most direct deliverable for the stated goal, and currently the least specified.

### M-6 — Determinism / injectable clock (A6 δ) is the precondition for the syntheses' own metamorphic/golden tests, yet it is omitted from every test-net recommendation. (MAJOR — the net can't be built without it)
A6 δ: `Date.now()/performance.now()/Math.random` appear 42× across 18 files *including the eval path* (`render-loop.ts`, `vector-tile-renderer.ts`, `label-pass.ts`). S4's entire net (golden-master, metamorphic "pan-and-back ⇒ identical", differential) requires deterministic frames. A scene whose evaluation reads un-injected wall-clock **cannot be golden-tested** — the same logical timestamp yields different frames. S4 lists `idle`/`error` as prerequisites but never lists clock injection, even though it is a harder and more pervasive blocker (42 sites vs one event). For a 4D goal where *time is the axis*, a non-injectable clock is doubly disqualifying. The reckoning prescribes a deterministic test net on top of a non-deterministic eval path and doesn't notice.
- **MUST:** Add "single injectable clock seam" as an explicit Phase-0/R2-level prerequisite of the test net, ranked with `idle`/`error`. The metamorphic and golden oracles are non-functional until it lands.

## THE INTEGRATOR'S BOTTOM LINE

The reckoning is an excellent diagnosis of the **2D-Mercator past** and a competent remediation plan for it. It is **not** a validated architecture for the **3D/4D/massive-data future** it claims to serve, and in four places (B-1, B-2, B-4, M-3) it commits the owner's named sin — trivializing the unbuilt future ("additive", "same wound", "reject ECS") to make the present plan feel complete. Before this synthesis is treated as a decision, the integrator MUST: (1) admit the forward axes (4D data model, 3D/depth/OIT, 3D-tiles plugin contract, cache-thrash under massive data) are *unscoped*, not *addressed*; (2) fix the keystone incoherence — GPU-CI cannot gate extrusion without a 3D oracle that does not exist; (3) move the two cheapest CRITICALs (packaging α, `error`-event/device-loss recovery) ahead of the multi-month god-file work; and (4) adjudicate the reversed-Z/OIT track the syntheses sequenced around but never analyzed.

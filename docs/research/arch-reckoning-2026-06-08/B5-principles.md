# B5 — Engineering Principles for Long-Term Structural Stability

**Scope:** DOD vs OOP / ECS · SOLID-at-scale failure modes · SAFE large-refactor · graphics/renderer testing · network backpressure for tile clients.
**Lens:** X-GIS = WebGPU + TypeScript web-map renderer, 5-year horizon, heading toward 3D-Tiles / 4D-city. Every principle below is followed by a **TRANSFER VERDICT** — does it hold for _this_ stack, and where does the analogy break? The owner is equally afraid of god-files **and** of speculative abstraction, so the bias throughout is: adopt the _force_, not the _ceremony_.

## (a) Data-Oriented Design vs OOP, and ECS

### The DOD thesis (Mike Acton)

Mike Acton's CppCon 2014 keynote "Data-Oriented Design and C++" (Engine Director, Insomniac Games) makes three load-bearing claims:

1. **"The purpose of all programs, and all parts of those programs, is to transform data from one form to another."** If you don't understand the data — its shape, volume, access pattern, and how it's _actually_ read/written at runtime — you don't understand the problem. ([isocpp.org summary](https://isocpp.org/blog/2015/01/cppcon-2014-data-oriented-design-and-c-mike-acton), [talk video](https://www.youtube.com/watch?v=rX0ItVEVjHc))
2. **Design around the "multiple" case, not the single case** — "there is never _one_ of anything important." The natural unit of work is a batch/array, not an object. ([isocpp.org](https://isocpp.org/blog/2015/01/cppcon-2014-data-oriented-design-and-c-mike-acton))
3. **The hardware is the platform.** OOP idioms (deep inheritance, virtual dispatch in hot loops, AoS layouts, "model the world as objects") are antithetical to performance because they scatter data and defeat the cache; restructuring data to fit cache lines yields **10×+** speedups. ([isocpp.org](https://isocpp.org/blog/2015/01/cppcon-2014-data-oriented-design-and-c-mike-acton), [graphicscompendium ch.62](https://graphicscompendium.com/software/09-data-oriented-design))

The canonical concrete pattern is **Struct-of-Arrays (SoA)** over Array-of-Structs (AoS): store each field in its own contiguous array so that a pass touching one field streams through memory with one cache miss per cache-line instead of one per element. ([dataorienteddesign.com](https://www.dataorienteddesign.com/dodmain/node12.html))

### Does DOD transfer to WebGPU/TypeScript?

**TRANSFER VERDICT: Partial — the _layout_ discipline transfers strongly; the _cache-line micro-optimization_ transfers weakly.**

- **What breaks the analogy:** Acton is reasoning about an L1/L2 cache hierarchy in native C++ on a fixed console target. In a V8/JIT TypeScript heap you do **not** control object layout — a plain JS object is a hidden-class-tagged, GC-managed, pointer-chasing thing, and you cannot lay out an array of them cache-tight. So "AoS vs SoA cache-line packing" as a CPU micro-optimization is mostly _unavailable_ to you at the JS-object level. ([thomcc.io: High-Performance JS via DOD](https://www.thomcc.io/2015/09/06/high-performance-javascript.html))
- **What transfers — and matters a lot:** The moment data crosses into a `TypedArray` (`Float32Array`/`Int32Array`) the layout _is_ yours and DOD becomes real again. The documented JS-DOD technique is exactly Acton's: **replace a list of JS objects with one or more typed arrays plus a manager.** ([thomcc.io](https://www.thomcc.io/2015/09/06/high-performance-javascript.html), [Weremczuk: DOD in the Frontend](https://medium.com/@pablo.weremczuk/data-oriented-design-in-the-frontend-part-2-data-locality-dff852f3800d)) For a GPU renderer this is doubly forced: **GPU buffers are SoA/packed-struct by nature** — vertex buffers, instance buffers, and uniform/storage buffers are flat typed memory with explicit strides. Your hot path is "transform tile features → packed GPU-ready bytes → draw calls," which is _literally_ Acton's rendering example ("scene objects → GPU-ready serialized data → render calls"). ([isocpp.org](https://isocpp.org/blog/2015/01/cppcon-2014-data-oriented-design-and-c-mike-acton))
- **Caveat from the DOD literature itself (anti-dogma):** SoA only wins when fields are accessed _separately_. If you always read x,y,z together, splitting them into three arrays forces **three** cache-lines instead of one — SoA then _loses_. Pick layout per access pattern, not by rule. ([data-structure-typed / DOD-in-frontend discussion](https://medium.com/@pablo.weremczuk/data-oriented-design-in-the-frontend-part-2-data-locality-dff852f3800d))

> **Rule for X-GIS:** Treat the codebase as two zones. (1) The **per-feature / per-vertex hot path** (tile decode → vertex/instance packing → draw) is a DOD zone: model it as typed-array columns and batch transforms, never as arrays of `Feature` objects walked one-by-one. This is already your reality — uniform packing, packed polygon/line vertices, RTC/ECEF buffers. (2) The **control plane** (map config, layer registry, style, lifecycle) is _not_ perf-critical and should stay readable OOP/plain-object code. DOD's payoff is in zone 1 only; applying it to zone 2 is the over-engineering Acton was _not_ arguing for.

### ECS — pros, cons, and when it helps

ECS (Entity-Component-System) stores entities as rows, components as columns, in **archetype tables** that are "fast to query and iterate" and "stored contiguously (in arrays)" enabling vectorization — i.e. ECS is DOD with an identity/query layer on top. ([Sander Mertens ECS-FAQ](https://github.com/SanderMertens/ecs-faq), [flecs.dev/ecs-faq](http://www.flecs.dev/ecs-faq/))

**Stated benefits (ECS-FAQ):** scales to large entity counts; composition is first-class (vs inheritance); reusable/extensible code; multithreading is _easier_ because data and behavior are separated so systems are independently parallelizable. ([ECS-FAQ](https://github.com/SanderMertens/ecs-faq))

**Stated costs (ECS-FAQ, and Mertens directly):** it "requires you to think about problems in a different way," is "hard to be a purist," and "hacks are sometimes applied to make ECS work" ([Mertens: Why Vanilla ECS Is Not Enough](https://ajmmertens.medium.com/why-vanilla-ecs-is-not-enough-d7ed4e3bebe5)); needs **glue code** to bridge native engine types ↔ ECS; "easy to learn, hard to master." Critically, the FAQ states ECS is **"generally not good at queries or operations that require highly specialized data structures, such as binary trees or spatial structures."** ([ECS-FAQ](https://github.com/SanderMertens/ecs-faq))

**TRANSFER VERDICT: Mostly NO for X-GIS's core; the _force_ behind ECS still applies.**

- A web-map renderer's dominant data structures are **spatial** — tile pyramids (quadtrees), R-trees for collision/labels, the tile cache, spatial index for picking. The ECS-FAQ explicitly names spatial structures and trees as ECS's _weak spot_. Your engine is the exact workload ECS is bad at. A general entity-with-arbitrary-components-and-queries runtime would be a speculative abstraction here.
- ECS shines when you have **many heterogeneous, dynamically-composed game objects** with cross-cutting per-frame systems (physics, AI, render) — Insomniac/Flecs game territory. X-GIS has a _small fixed set_ of layer kinds (fill, line, symbol, raster, extrusion) over _massive homogeneous_ geometry. The variety is in _layers_, not in _entities_; the volume is in _vertices_, not in _components_. That argues for **per-layer SoA pipelines**, not a generic ECS.
- The part that _does_ transfer is ECS's underlying instinct, which is just DOD: **separate data (component columns) from behavior (systems that sweep columns).** You can adopt that as a discipline — "a render pass is a system that sweeps a typed-array column of features" — without importing an ECS framework, its query engine, or its archetype churn. The 4D/temporal-city direction may later create a genuine many-heterogeneous-objects scene (movable assets, simulation agents over time) where a _scoped_ ECS for the 3D scene-graph layer is defensible — but gate that on the Rule of Three (below), not on aspiration.

> **Rule for X-GIS:** Do **not** adopt an ECS framework for the map/tile core — your hot data is spatial, which is ECS's documented weakness, and a generic entity/query runtime is exactly the speculative abstraction to avoid. **Do** keep ECS's data↔behavior separation as a coding discipline (passes sweep typed-array columns). Revisit a _narrowly scoped_ ECS only if the 4D-city scene introduces genuinely many heterogeneous dynamic objects — and only after three concrete cases exist.

## (b) SOLID at Scale — when SRP / DIP / abstraction BACKFIRE

SOLID is sound in the small. At scale, each letter has a failure mode that produces the _opposite_ of maintainability — and these are well-documented, not heresy.

- **Over-abstraction is the dominant SOLID failure.** "The biggest trap is over-engineering — splitting code into layers of abstractions that serve no purpose. When every feature spawns a new interface or base class, complexity explodes and maintainability disappears." The biggest _cost_ of overusing SOLID is **reduced readability**: if a simple function requires navigating multiple abstract classes, interfaces, and DI wiring, the code is harder to follow, not easier. ([JavaCodeGeeks: The Dark Side of Clean Code](https://www.javacodegeeks.com/2026/05/the-dark-side-of-clean-code-when-solid-and-dry-principles-actively-hurt-you.html), [Baeldung: When SOLID May Not Be Appropriate](https://www.baeldung.com/cs/solid-principles-avoid))
- **Premature abstraction / DIP-everywhere.** "Wrapping a single logging call behind an elaborate interface before understanding your domain creates unnecessary indirection and slows delivery." DIP applied before you know the domain produces interfaces with exactly one implementation — pure indirection tax. ([JavaCodeGeeks](https://www.javacodegeeks.com/2026/05/the-dark-side-of-clean-code-when-solid-and-dry-principles-actively-hurt-you.html))
- **The counter-rule: Rule of Three / AHA.** "Wait until you have three similar implementations before extracting a shared abstraction." Sandi Metz's **AHA — Avoid Hasty Abstractions** — explicitly resists abstracting immediately; let abstractions _emerge from concrete examples_ once the true requirements are clear. **"Prefer duplication over the wrong abstraction"** — a wrong abstraction is more expensive to undo than duplication. ([lostechies: Rule of Three](https://lostechies.com/derickbailey/2012/10/31/abstraction-the-rule-of-three/), [holdenrehg: Rule of Three](https://holdenrehg.com/blog/2021-09-20_rule-of-three), [JavaCodeGeeks](https://www.javacodegeeks.com/2026/05/the-dark-side-of-clean-code-when-solid-and-dry-principles-actively-hurt-you.html))
- **DRY's dark side.** Forcing two superficially-similar-but-semantically-different code paths through one abstraction couples things that should evolve independently — a frequent root cause of "fix here breaks there." DRY is about _knowledge_ duplication, not _text_ duplication. ([Medium: Dark Side of DRY](https://medium.com/@ss-tech/the-dark-side-of-dont-repeat-yourself-2dad61c5600a))
- **Context dominates.** "A startup iterating toward product-market fit needs code that is easy to delete and rewrite. Premature SOLID compliance leads to constant refactoring of abstractions created before the business direction was clear." Small, well-defined units don't need layered abstraction at all. ([Baeldung](https://www.baeldung.com/cs/solid-principles-avoid), [JavaCodeGeeks](https://www.javacodegeeks.com/2026/05/the-dark-side-of-clean-code-when-solid-and-dry-principles-actively-hurt-you.html))

**TRANSFER VERDICT: YES, directly — and it maps onto X-GIS's _existing_ documented tension.** X-GIS already has both pathologies on record: god-files (VTR ~5600 LOC, map.ts ~2800) **and** an authority-inversion where the PROJECTIONS table is pinned to scattered shader literals (the "common root of all audits"). Both letters of the failure spectrum are live. SOLID-at-scale gives the discriminator: god-files are a _real_ SRP violation worth fixing; but the fix is **not** "an interface per concern" — that risks trading a 5600-line file for 40 files of one-implementation interfaces you must hold in your head at once.

> **Rule for X-GIS:** Decompose god-files toward **named seams with concrete collaborators**, not toward abstract interfaces. Apply the **Rule of Three**: do not introduce an interface/DI boundary until a _third_ real implementation or a _real_ test seam demands it. Concretely — the documented #1 debt (PROJECTIONS table as authority, shader literals as data _generated from_ it) is a _good_ abstraction because there are genuinely 7+ projections (well past three) and the duplication is causing real bugs; that earns its abstraction. A `ITileFetchStrategy` with one implementation does not. The test: every abstraction must point to ≥3 concrete consumers _today_ or remove a _current_ duplication-driven bug class.

## (c) SAFE large-refactor of a fragile renderer — NO big-bang

Four interlocking techniques, all aimed at "the code works at every commit; rollback is one revert."

### 1. Strangler Fig (Fowler)

Build the new implementation _alongside_ the old, behind a façade that routes requests, and **incrementally move behavior** from old to new until the old "host" can be deleted. The explicit rationale is **risk**: "the most important reason to consider a strangler application over a cut-over rewrite is reduced risk… a strangler can give value steadily and the frequent releases allow you to monitor its progress more carefully." Big-bang rewrites fail because "it's hard to figure out the details of existing behavior." Caveat: you must accept **transitional/scaffolding code** that exists only to let old+new coexist and is deleted at the end. ([Fowler: Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html))

### 2. Branch by Abstraction (Fowler / Continuous Delivery)

For changes _inside_ a module where a façade is awkward: (1) introduce an abstraction layer over the current supplier; (2) move all clients onto it (improving test coverage as you go); (3) build the new supplier behind the same abstraction; (4) switch clients over, then delete the old supplier. **"Your code is working at all times throughout the re-structuring"**; both implementations can be live simultaneously (often behind a flag), so a big-bang replacement becomes "a series of small, reviewable changes. Each commit stays deployable. Rollback is instant." ([Fowler: Branch By Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html), [continuousdelivery.com](https://continuousdelivery.com/2011/05/make-large-scale-changes-incrementally-with-branch-by-abstraction/))

### 3. Characterization / Golden-Master tests (Feathers)

"A characterization test is a test that **characterizes the actual behavior** of a piece of code." You don't assert what the code _should_ do — you snapshot what it _does_ now, so that any refactor that changes behavior trips the test. This is the safety net that makes 1 & 2 safe on code whose spec is unknown. ([understandlegacycode summary](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/))

### 4. Feathers' machinery — seams & the change algorithm

- **"Legacy code is code without tests."** No tests → no safety net → no safe change. ([understandlegacycode](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/))
- A **seam** is "a place where you can alter behavior in your program without editing in that place" — the insertion point for a test where none existed. ([understandlegacycode](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/))
- **Change algorithm:** identify change points (seams) → break dependencies → write characterization tests → make the change → refactor. ([understandlegacycode](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/))
- **Sprout & Wrap** for when there's no time to test the surrounding mess: _Sprout_ new logic into an isolated tested method called from the untested code; _Wrap_ the old method (rename it, add a tested wrapper) instead of editing it in place. ([understandlegacycode](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/))

**TRANSFER VERDICT: YES — and this is the highest-value transfer in this whole document, _because_ X-GIS's pain is "fix doesn't hold / fixing bug A reopens bug B."** Fowler/Feathers were written for native and server code, but the techniques are language-agnostic structural moves. The one adaptation: X-GIS's "characterization test" can't be a CPU-value snapshot for render behavior — it must be a **golden-master rendered image** (see section d). That's not a weakening; it's the correct oracle for a renderer.

> **Rule for X-GIS:** Forbid big-bang rewrites of any render-path subsystem. For each fragile area: (1) lock a **golden-master image suite** across the real output space _before_ touching code (the characterization test); (2) introduce a **Branch-by-Abstraction seam** (e.g. an interface boundary around the projection emitter, or the tile-fetch scheduler) so old and new coexist behind a flag; (3) migrate consumers one at a time, each commit green and revertible; (4) delete the old path only when the golden suite is identical. Use **Sprout** for new behavior so you never edit the 5600-line VTR in place — you call into a new tested unit from it. This directly attacks the "predictability sinks / fix doesn't hold" failure mode already on record.

## (d) Testing strategy for a GRAPHICS renderer

### Why "it compiles, unit tests pass, but it renders wrong" happens

This is the **oracle problem**: "the difficulty of determining the expected outcomes… or whether the actual outputs agree with the expected outcomes." For a renderer the output is an under-specified image — there is no cheap function that says "this frame is correct." ([Wikipedia: Metamorphic testing](https://en.wikipedia.org/wiki/Metamorphic_testing)) Unit tests check **component math on the CPU** (a matrix multiply, a clip computation); the bug lives in the **rendered output** under axis combinations the unit tests never exercise (projection × pitch × deep-zoom × real-data × cross-surface). The shader-compiler literature names this directly: "a key challenge… is the lack of an oracle that classifies an output as correct or incorrect; this is particularly pertinent in graphics shader compilers where the output is a rendered image that is typically under-specified." ([marktechpost: PBT guide](https://www.marktechpost.com/2026/04/18/a-coding-guide-for-property-based-testing-using-hypothesis-with-stateful-differential-and-metamorphic-test-design/), [arxiv: Surfacing Visualization Mirages](https://arxiv.org/pdf/2001.02316))

> _(This is exactly X-GIS's standing finding: "many unit tests yet bugs keep coming — tests verify component math (CPU), bugs live in rendered output under untested axes; CI has no GPU so no visual gate." The external literature confirms it's a structural property of graphics testing, not a discipline failure.)_

### The four oracles that actually catch render bugs

1. **Golden-master / visual-regression.** Compare a captured frame buffer against a stored known-good reference. This is the renderer's characterization test. ([ijetcsit: GPU frame-buffer regression](https://ijetcsit.org/index.php/ijetcsit/article/view/722), [JuliaPlots/VisualRegressionTests.jl](https://github.com/JuliaPlots/VisualRegressionTests.jl), [BrowserStack: Visual Regression Testing](https://www.browserstack.com/percy/visual-regression-testing)) **Known failure mode you must design around:** exact pixel/hash comparison is "precise but sensitive to minor rendering variations… minor rendering differences between device GPUs can cause failures even if the UI looks fine to humans." Different OS/driver/GPU produce sub-pixel AA differences. ([Medium: VRT Best Practices](https://medium.com/@ss-tech/the-ui-visual-regression-testing-best-practices-playbook-dc27db61ebe0), [BrowserStack](https://www.browserstack.com/percy/visual-regression-testing)) Mitigation: **tolerance/perceptual diffing** (e.g. odiff-style with AA handling) over MD5/exact hashing for cross-GPU stability, reserving exact hashing for same-GPU drift detection. ([ijetcsit](https://ijetcsit.org/index.php/ijetcsit/article/view/722), [Medium VRT](https://medium.com/@ss-tech/the-ui-visual-regression-testing-best-practices-playbook-dc27db61ebe0))
2. **Metamorphic testing** — the oracle-problem escape hatch. You don't need the "correct" image; you assert **relations between multiple runs**: a _semantics-preserving transform of the input must produce an equivalent output._ This is exactly how **GraphicsFuzz** (Imperial College → acquired by Google, Aug 2018) tests GPU drivers/shader compilers: apply semantics-preserving shader rewrites and require the rendered image to be **identical** — any divergence is a driver/compiler bug. ([Wikipedia: Metamorphic testing](https://en.wikipedia.org/wiki/Metamorphic_testing)) For a map renderer, metamorphic relations are abundant and cheap: pan-by-one-tile-then-pan-back ⇒ identical frame; world-copy wrap ⇒ identical content one world over; same scene via two equivalent projection code-paths ⇒ identical pixels; zoom-out-then-in to same z ⇒ stable.
3. **Differential testing** against a reference renderer (a second oracle): same style + same camera through X-GIS vs a trusted reference (MapLibre / d3-geo numeric) and diff. ([marktechpost](https://www.marktechpost.com/2026/04/18/a-coding-guide-for-property-based-testing-using-hypothesis-with-stateful-differential-and-metamorphic-test-design/)) _(X-GIS already does the numeric flavor of this with d3-geo — extend to pixel-differential where a reference exists.)_
4. **Property-based testing** of invariants — "specifying invariants — rules that always true regardless of input — rather than checking specific input→output pairs," generating thousands of random inputs to falsify them. ([marktechpost](https://www.marktechpost.com/2026/04/18/a-coding-guide-for-property-based-testing-using-hypothesis-with-stateful-differential-and-metamorphic-test-design/), [innoq: fast-check](https://www.innoq.com/en/articles/2023/04/testing-fast-check/), [yrkan: PBT](https://yrkan.com/blog/property-based-testing/)) Renderer invariants: every on-screen feature anchor projects to within-canvas bounds; tile coverage has no gaps/overlaps; label collision is idempotent; forward∘inverse projection ≈ identity within ε.

### The pyramid for GPU code

The classic pyramid (many fast unit tests, fewer integration, few E2E) **inverts in emphasis** for renderers: the cheap CPU-unit layer is _necessary but proven insufficient_ (it's where X-GIS already lives and bugs still ship). The decisive layer is the **visual/integration tier that requires a real GPU**, which CI-without-GPU cannot provide — confirmed by the GPU-frame-buffer regression literature and by X-GIS's own "CI = no-GPU = no visual gate" finding. ([ijetcsit](https://ijetcsit.org/index.php/ijetcsit/article/view/722)) The practical resolution in the field: run the visual tier on a **real-GPU lane** (local/desktop or GPU-equipped runner), treat SwiftShader/CI as a _compile + math_ gate only.

**TRANSFER VERDICT: YES, with a hard constraint X-GIS already discovered — the visual oracle MUST run on a real GPU, and MUST be a MATRIX across the output space (projection × pitch × zoom × data × surface), not a handful of Mercator views.** A single golden view is a tripwire, not a gate; bugs hide in the _combinations_.

> **Rule for X-GIS:** Layer four oracles, not one. (1) CPU **property-based** invariants (fast, CI, falsify projection/coverage/collision math with `fast-check`). (2) **Golden-master image MATRIX** on a real-GPU lane, perceptual-tolerance diff for cross-GPU stability, spanning the _combinatorial_ output space — this is your renderer characterization test and the gate for every render-path refactor. (3) **Metamorphic relations** (pan-and-back, world-copy, dual-projection-path equivalence) to get correctness signal _without_ a ground-truth image — the cheapest way to expand coverage. (4) **Differential** vs d3-geo/MapLibre where a reference exists. Never let "unit tests green" stand in for "renders right" — the literature says that gap is structural, not fixable by adding more unit tests.

## (e) Network backpressure / concurrency / priority queues for the tile client

A tile client that fires every needed tile at once floods the connection pool, starves interaction, and wastes bandwidth on tiles the user already panned past. MapLibre's hard-won mechanisms:

- **Throttle while moving.** "The image request queue can cause frame-rate glitches while the map is moving; the renderer can throttle the requests processed by the image request queue until the map stops moving again." Don't issue full-rate fetches mid-gesture. ([MapLibre PR #2097](https://github.com/maplibre/maplibre-gl-js/pull/2097))
- **Priority + viewport-edge demotion.** Limit concurrent server requests; **lower the priority of viewport-border tiles** so center-of-screen tiles win the connection budget. ([maplibre-preload](https://github.com/AbelVM/maplibre-preload), [maplibre #116: prefetch strategy](https://github.com/maplibre/maplibre-gl-js/issues/116))
- **Cancellation / abort on intent change.** "Pending requests can be canceled if the movement has ended, the time limit is met, or a new movement is started"; custom protocol handlers receive an **`AbortController`** to cancel in-flight fetches. When the user keeps panning, in-flight requests for now-off-screen tiles should be aborted, not awaited. ([maplibre-preload](https://github.com/AbelVM/maplibre-preload), [MapLibre addProtocol docs](https://maplibre.org/maplibre-gl-js/docs/API/functions/addProtocol/))
- **Dedup repeated requests.** Avoid re-requesting a source's tile that's already pending/cached — a documented MapLibre bug class. ([maplibre #4074](https://github.com/maplibre/maplibre-gl-js/issues/4074))
- **Explicit concurrency cap.** Independent of the engine, a hard `tileRequestLimit` on concurrent connections is a standard guard. ([staticmaps #36](https://github.com/StephanGeorg/staticmaps/issues/36)) The transport matters too: under HTTP/1.1 the browser's ~6-connections-per-host limit _is_ the cap and head-of-line blocking bites; HTTP/2 multiplexes many tiles over one connection, changing the optimal concurrency. ([openlayers #7101: HTTP/2 concurrent tiles](https://github.com/openlayers/openlayers/issues/7101))

**TRANSFER VERDICT: YES, almost 1:1 — these were designed for exactly this problem (a browser tile client) and X-GIS _is_ that.** The only deltas are upside: WebGPU/modern fetch gives you `AbortController` natively, and X-GIS already has a documented **PriorityQueue + staging-buffer pool + prewarm** async pipeline — so this is _validation and hardening_ of an existing design, not a new build. The 3D-Tiles/4D direction makes it _more_ important: 3D-Tiles fetches are larger and hierarchical (bounding-volume traversal), so screen-space-error-driven priority + abort-on-camera-change becomes the dominant perf lever, not an optimization.

> **Rule for X-GIS:** The tile scheduler is a first-class subsystem with five invariants: (1) **bounded concurrency** (a hard in-flight cap, tuned to HTTP/2 vs HTTP/1.1 reality); (2) **priority queue** keyed by screen-space error / distance-to-viewport-center (center beats edge, visible beats prefetch); (3) **abort on intent change** — cancel in-flight fetches for tiles that left the frustum via `AbortController`, never await dead work; (4) **throttle during active gestures**, full-rate when settled; (5) **dedup** — one in-flight request per tile key, ever. Treat these as testable invariants (property-based + integration), because under 3D-Tiles/4D load this scheduler, not the GPU, becomes the bottleneck.

## Cross-cutting synthesis for the 5-year decision

1. **Adopt DOD's _force_ (typed-array SoA in the hot path, GPU buffers are already this) — reject its _micro-cache dogma_** (you don't own JS-object layout) and **reject a general ECS** (your core data is spatial = ECS's documented weakness). DOD lives in zone 1 (per-vertex/per-feature); zone 2 (control plane) stays readable OOP.
2. **SOLID failure mode is the owner's exact fear made concrete:** the cure for god-files is **named seams with concrete collaborators + Rule of Three**, never an interface per concern. Earn every abstraction with ≥3 real consumers or a real current bug class (the PROJECTIONS-table abstraction earns it; a one-impl strategy interface does not).
3. **All future structural change goes through Strangler Fig / Branch-by-Abstraction with golden-master characterization first** — big-bang rewrites of the render path are forbidden. This is the direct antidote to the recurring "fix doesn't hold."
4. **Testing must be a four-oracle matrix on a real GPU** (property-based invariants + golden-master image matrix + metamorphic relations + differential), because "compiles + unit-green ≠ renders right" is a _structural_ property of graphics testing per the literature, not a discipline gap to be closed with more unit tests.
5. **The tile scheduler is a named subsystem with five testable invariants** (bounded concurrency, SSE-priority queue, abort-on-intent, gesture throttle, dedup) — and it _grows_ in importance under 3D-Tiles/4D.

## 1. The key observation: these are one shader, not three

Every property above is a function of **the camera ray direction at a pixel**, resolved
against two vectors: the local **zenith** and (for the sun-relative arms) the **sun**.

- MapLibre `sky` root is a gradient in **zenith angle**: `sky-color` at the zenith →
  `horizon-color` at the horizon (`sky-horizon-blend` sets the width) → `fog-color` below it
  (`fog-ground-blend`).
- Mapbox `sky` layer / `sky-type: gradient` is a gradient in **radial progress** about
  `sky-gradient-center` — the same 1-D ramp, re-parameterised by angle from a chosen axis
  instead of from the zenith. `sky-radial-progress` is already a `na` expression row
  (`spec-coverage/expressions.ts:244`) precisely because it only means anything inside this ramp.
- Mapbox `sky` layer / `sky-type: atmosphere` is the same ramp plus a **sun-relative halo**
  (`sky-atmosphere-sun`, `-halo-color`).
- Mapbox `fog` root is a gradient in zenith angle too — `color` near the ground,
  `high-color` in the upper atmosphere, `space-color` past the horizon, `horizon-blend`
  as the transition width — **plus** one genuinely different term: `range`, a per-fragment
  _distance_ attenuation. §5 is entirely about that one term.

So: **one `f(dot(ray, up), dot(ray, sun))` evaluator serves rows 1, 2, and the
direction-dependent 6/7 of row 3.** Three converter front-ends, one renderer.

### And that renderer already exists

`map/src/render/passes/atmosphere-pass.ts` + `map/src/render/atmosphere-uniform.ts` +
`map/src/shaders/dsl/atmosphere.ts` (#1258) already:

- run in the **exact pass slot** sky needs — `PASS_CHAIN_ORDER` position 1, immediately after
  `background` and before every geometry draw, so painter's order is
  space → sky → earth → content (`pass-order.ts:20-27`);
- reconstruct the per-pixel world-space camera ray from four CPU-unprojected NDC corners
  (`atmosphereCameraRays`) and hand the shader `eye`, the four `ray_*`, and `up`
  (`localFrame(centerLon, centerLat).up`) — **the exact inputs §1 says the evaluator needs**;
- emit **both** backends from one DSL module (`emitAtmosphereWgsl` / `emitAtmosphereGlslStages`),
  which is the ADR-0003 property this work must not break;
- carry a real-GPU gate (`playground/e2e/_atmosphere-globe-gate.spec.ts`), backend-parameterised
  and asserting `window.__xgisActiveBackend` so a silent fallback cannot green it.

**Consequence that shapes the whole plan: rows 1 and 2 are a shader-body and converter
change inside an existing pass, not a new pass.** `pass-order.ts` and `pass-chain.ts` are
not touched at all. The "pass registry hookup" the track brief budgets as its one
shared-file touch turns out not to be needed.

### Row 2 is literally #1258's own deferred Phase 2

`map.ts:1099-1103` says so in the source:

> `#1258` — set the top-level atmosphere/sky. Mirrors `setLight` / `setBackgroundFill`: a
> top-level style concern threaded straight to the render host, **not (yet) a style-spec
> JSON property (Phase 2, per the issue)**.

`setAtmosphere` has **no caller anywhere outside its own tests** — the #1258 Phase 1 work
shipped the pass, the uniform, the shader and the GPU gate, and stopped one step short of
parsing a style. Row 2 is that step. This is not a coincidence to note in passing; it means
row 2's renderer risk is already retired and its remaining work is converter + host wiring.

## 2. What we are NOT doing (rejected, with reasons — do not re-propose without new facts)

**A dome quad.** `SKIP_REASONS` currently advertises "would need a dome quad +
per-fragment hue interpolation" (`layers.ts:17`). A dome is a mesh whose vertices must be
projected — which under ADR-0005's logic means a _second_ geoid, a second world-copy story
and a second projection path, the exact thing deleting `BackgroundRenderer` bought us out
of. It also has to be tessellated finely enough to hide banding on the horizon. The
fullscreen-triangle + per-pixel ray the atmosphere pass already uses is strictly better:
no mesh, no projection path, exact silhouette. **The SKIP_REASONS text is wrong and its
correction is part of the row-1 phase.**

**A 2-D screen-space gradient keyed to a screen circle/line.** Rejected for the reason
`shaders/dsl/atmosphere.ts`'s own header already records: under pitch and bearing the
globe silhouette is not a screen circle and the flat horizon is not a screen row, so a 2-D
approximation drifts off the true horizon exactly where the gradient is steepest. The
ray-based test is geometric and costs the same.

**Extending the background pass instead.** The background pass is a _clear_ — a pure
`backgroundClearValue(projType, bg, overdraw)` function, deliberately not a fullscreen
quad (ADR-0007 §Consequences bullet 2). Turning it into a shaded quad would give it two
jobs and re-open the ownership question ADR-0007 closed. The atmosphere pass exists
because ADR-0007 explicitly split this concern out; use it.

**A post-process depth-mixing fog pass.** This is what `spec-coverage/top-level.ts:66`
currently promises. §5 shows it is the wrong shape, and the row's note is corrected in the
final phase.

**Re-introducing black above the horizon.** ADR-0007 deliberately reversed the iter-196
black-outside-world convention for flat CORE/SHOWCASE: every viewport pixel must have a
defined source. A sky that paints over the above-horizon region must therefore _replace_ a
defined background with a defined sky, never expose a void. `_coverage-black-ratio.spec.ts`
is the standing gate and must not regress in any phase.

**A scattering model.** `sky-atmosphere-*` names Rayleigh-ish concepts but Mapbox's own
implementation is a parameterised gradient, not a simulation. `atmosphere.ts`'s header
already commits to "a gradient, not a model". Unchanged.

## 3. Where the horizon _is_ — the one real fork

The evaluator in §1 needs the horizon. Its definition differs by projection class, and
this is the fork that actually costs work.

**Globe class** (`worldBand === 'sphere-full'`, projTypes 3/4/5/7). The horizon is the
sphere limb, and the exact test is ray–sphere closest-approach — already implemented in
`fs_atmosphere` (`tca`/`closest`/`distClosest`). Zenith angle comes free as
`dot(normalize(ray), up)`.

**Flat / cylindrical class** (`worldBand ≠ 'sphere-full'`, projTypes 0/1/2/6). There is no
limb. The horizon is the **vanishing line of the ground plane** under the current MVP: the
set of ray directions with `dot(ray, up) == 0`. So the same `dot(ray, up)` term _is_ the
flat horizon test, with no sphere math at all — the ray field is already in world space and
`up` is already a uniform.

That symmetry is worth stating plainly because it is what makes the flat arm cheap: **the
zenith-angle gradient needs no per-projection branch.** Only the _limb-glow band_ (the
existing #1258 effect, which measures distance to the sphere) is globe-specific.

But two things do NOT come free on the flat arm, and they are the row-2/row-1 risk:

1. **The existing pass is gated OFF on flat.** `scene-view.ts:122` computes
   `hasAtmosphere = host._atmosphere !== null && host.camera.globeMode`, and
   `atmosphere-pass.ts` re-guards on `camera.globeMode` in its body. The gate is correct
   _for a ray–sphere effect_ — its header explains at length that running 3-D ECEF camera
   math against a flat 2-D disc's world space describes a camera that is not on screen.
   Opening the pass to flat projections therefore requires proving the flat MVP's
   `atmosphereCameraRays` output is meaningful, not just deleting the `&&`. This is the
   single most likely place for this track to produce a plausible-looking wrong render.
2. **Flat merc at pitch already paints the style background above the horizon** (ADR-0007).
   Sky _replaces_ that region rather than filling a void, so the visual delta is
   background-colour → sky-gradient, and the before/after gate must assert exactly that
   (DC > 0 in the above-horizon band, black-ratio unchanged at 0).

## 4. The `sky-opacity` / `atmosphere-blend` seam

Both specs carry a global fade (`sky-opacity`, MapLibre `atmosphere-blend`) that is
zoom-dependent in every real style — the standard MapLibre idiom fades the sky out as you
zoom in past the point where the horizon leaves the screen. This resolves through the
existing zoom-expression machinery on the converter side and arrives at the host as a
single scalar per frame, multiplied into the shader's output alpha. No new plumbing.

One constraint discovered while reading: the pass writes with `loadOp: 'load'` and never
claims `resolveTarget` (`atmosphere-pass.ts`, and `pass-order.ts:20-27` records the same
for the slot). At `sky-opacity: 0` the pass must therefore **not run at all** rather than
draw a transparent quad, so the frame stays byte-identical to sky-off. That is a
`shouldRun` predicate, and it is what keeps the byte-identity invariant (ADR-0012 §4.3)
purchasable for every style that does not author a sky.

## 5. Fog: why "a post-process pass with depth-based mixing" is the wrong shape

The spec-coverage note has been the plan of record for this row. Reading the code, it does
not survive contact. Four findings, in ascending order of how expensive they were to get:

**(a) There is no sampleable depth today.** The depth-stencil is `depth24plus-stencil8`
(`pipeline-factory.ts:855, :956`) and reaches passes only as an _attachment_ view,
`ctx.rhiStencilView` (`frame-context.ts:85-90`). Sampling it means adding `TEXTURE_BINDING`
usage at the render-target allocator — engine-side, shared, and outside this track's
"new modules under `map/src/render/`" boundary.

**(b) The two backends need two different shader bodies.** `maxSampleCount` is **4 on
WebGPU and 1 on WebGl2Device** — pinned, with the reason, by
`frame-context-samplecount-clamp.test.ts:1-10` ("its screen pass has no MSAA resolve").
So the same effect needs `texture_depth_multisampled_2d` + `textureLoad(…, sample)` on
WebGPU and a plain depth sample on WebGL2. ADR-0003's whole point is that one DSL module
emits both backends; a sampled-depth fog is the first effect that would _structurally_
resist that, and it would need a new sampled-texture type in the DSL to even express.

**(c) It inherits ADR-0007's deferred MSAA resolve-owner centralization.** ADR-0007
§Consequences bullet 3 deferred that work with an explicit trigger:

> centralization is only needed when a _late_ colour pass (the atmosphere pass) is added,
> and is tracked with that work.

The atmosphere pass dodged this by landing _early_ (slot 1, pre-geometry, never the last
colour writer). A fog post-process is by definition **late** — it must run after the
geometry whose depth it reads. So it, not #1258, is the trigger. **A post-process fog
therefore silently carries a second, unbudgeted, cross-cutting refactor.**

**(d) Mapbox does not do it this way either.** Mapbox GL JS applies fog _per drawable_, in
each program's fragment shader, from the fragment's own position — not as a screen-space
depth composite. Reconstructing view distance from a non-linear `depth24plus` sample means
inverting the projection per pixel, which for the ECEF/globe ladder is exactly the
cancellation-prone algebra `unproject-dsl.ts`'s header exists to warn about. **The
fragment shaders already have the world position; the post-process would be throwing it
away and paying to reconstruct it badly.**

### The honest counter-argument

Forward fog is _wide_: it touches the fragment tail of polygon / line / point / raster
(and label), and the polygon byte-drift snapshot gate (`polygon-variant-diff.test.ts`,
≥8 committed fixtures under `__polygon-variant-snapshots__/`) goes red across all of them
and needs a deliberate `bun scripts/capture-polygon-snapshots.ts` recapture. A
post-process pass is _narrow_: one module, one slot. Narrowness is a real virtue and this
document should not pretend otherwise.

The tiebreaker is **what can ship with a gate at each step**. Forward fog can go one
surface at a time, each increment with its own snapshot recapture and its own pixel gate,
and each increment is independently revertible. The post-process cannot: the depth-usage
change, the DSL sampled-depth type, the two-backend divergence and the resolve-owner
centralization must ALL land before a single fog pixel appears — one unverifiable
big-bang, which is precisely the shape ADR-0009 §Consequences forbids for this codebase's
god-files ("must be staged and individually verified, NOT a big-bang rewrite").

### So fog splits in two, and only the cheap half is scheduled here

Re-read the spec: 6 of `fog`'s 7 properties (`color`, `high-color`, `space-color`,
`horizon-blend`, `star-intensity`, `vertical-range`) are **direction**-dependent — they are
§1's evaluator, and they cost approximately nothing once rows 1–2 land. Exactly one,
`range`, is **distance**-dependent and needs per-fragment depth.

That is the natural cut:

- **Fog tier 1 (scheduled, §6 Phase 4)** — the direction-dependent 6, through the same
  sky evaluator. Ships as `partial` with a warning that names `range` and the reason.
  This is the visually dominant half: the horizon haze band _is_ what "fog" looks like in
  a Mapbox v3 style at typical camera angles.
- **Fog tier 2 (NOT scheduled here)** — `range` as forward, in-shader per-fragment
  attenuation, one surface per increment. Gated behind measured evidence that tier 1's
  residual is visible on a real style. If it clears that bar it is its own design doc and
  its own ADR-0012 item, because it re-opens the surface shaders.

A `partial` row with a precise warning is an ADR-0012 §1 endpoint in good standing ("or
`partial` with a **precise, warning-backed degradation note**"), not a shortfall.

## 6. Phases

Each phase is one shippable unit: issue → fail-before corpus → change → full local gate
(`bun run build` + `bun run test`, **sequential**, CLAUDE.md §7) → draft PR. Fetch and
merge `origin/main` before each (four tracks are live). Byte-identity snapshots wherever
converter output moves.

### Phase 0 — make room in `map.ts` (pure extraction, no behaviour change)

**`map/src/map.ts` is at 5623 lines against a ceiling of exactly 5623**
(`loc-ceiling-ratchet.test.ts:749`). Zero headroom. The ratchet is shrink-only and this
track is instructed to extract, never bump — so _no_ host state can land in `map.ts` until
something leaves it. #1258 itself paid 5497→5546 for `_atmosphere` + `setAtmosphere` with
a ceiling bump; that route is closed now.

Extract the top-level style host-state family — `_light` / `setLight`,
`_atmosphere` / `setAtmosphere`, `_backgroundColor` / `setBackgroundFill` — into a new
`map/src/style-top-level.ts`, leaving `map.ts` the composition-root delegation only.
**Lower** `map.ts`'s ceiling by the extracted count. This creates the module that rows 1–3
then extend, so every later phase's host change costs `map.ts` nothing.

- Fail-before: the ratchet with a deliberate +1 line in `map.ts` must go red first (proves
  the ceiling is live, per the §12 "vacuously green gate" lesson).
- Gate: full suite green, ceiling lowered, `git show --stat HEAD` read against intent
  (§12: a gate that ran before the state you commit did not gate it).
- No GPU tier — no pixel moves.

- Fail-before: a corpus style authoring `sky` must show the gradient absent, then present.
- §5 gate: extend `_atmosphere-globe-gate.spec.ts` — both backends, backend asserted.
- Byte-identity: all 9 audited styles that do not author `sky` stay byte-identical.

### Phase 2 — flat / cylindrical arm

Open the pass to `worldBand ≠ 'sphere-full'`. The gate change in `scene-view.ts:122` is
**one line and the whole risk of this track** (§3.1) — it is paired with a proof that

The limb-glow term stays globe-gated; only the zenith gradient opens up.

- Fail-before: a metamorphic sweep over pitch × zoom × projType asserting the horizon the
  shader computes matches the CPU ground-plane vanishing line (ADR-0009's "verify by
  domain invariant, not pinned example").
- §5 gate: new pitched-Mercator spec — above-horizon band DC > 0, and
  `_coverage-black-ratio.spec.ts` still ≤ 2 % black (ADR-0007 must not regress).

### Phase 3 — Mapbox `sky` LAYER

Converter lifts `sky-type: gradient` (via `sky-gradient` / `-center` / `-radius`) and

- Fail-before: a fixture with each `sky-type`, red then green.
- Byte-identity: mandatory — this changes `convertLayer`'s dispatch.

### Phase 4 — `fog` root, tier 1

Direction-dependent 6 properties through the same evaluator (§5). `range` warns precisely.

### Phase 5 (FINAL, and the only phase that touches shared status files)

`spec-coverage/layer-types.ts` (`sky` → `supported`), `spec-coverage/top-level.ts`
(`sky` new row; `fog` → `partial`, note corrected off "post-process pass with depth-based
mixing"), regenerate `scripts/gap-matrix.md`, and the matching `RUNTIME_CAPABILITIES` rows.

**This is a THREE-way sync, not a one-line edit** (§12): spec-coverage row + regenerated
gap-matrix + `RUNTIME_CAPABILITIES` (`map/src/capabilities.ts:37`). **Two** drift gates
guard it, with different tolerances, and both must be satisfied:

- `compiler/src/__tests__/spec-coverage-drift.test.ts:333-338` — a row marked `supported`
  whose converter source has no matching reference is an orphan, and the assertion is
  `toEqual([])`: **zero tolerance**.
- `map/src/__tests__/spec-coverage-runtime-drift.test.ts:245` — `expect(orphans.length)
.toBeLessThan(3)`: a _budget_, currently near its limit, so a forgotten
  `RUNTIME_CAPABILITIES` row can breach it on its own.

`emit-gap-matrix.ts` writes to **stdout** by contract (its own header: "Run via:
`bun scripts/emit-gap-matrix.ts > scripts/gap-matrix.md`") — exit 0 ≠ file written (§12).

Deferred by design, recorded here so it is not re-derived: **fog tier 2** (`range`,
forward per-fragment), and with it ADR-0007's MSAA resolve-owner centralization, which
tier 2 — not #1258 and not this track's tier 1 — is the actual trigger for.

## 8. Verification posture

Per ADR-0004 and CLAUDE.md §5, every phase that moves pixels owes a real-GPU tier, and
**both backends run headlessly here on SwiftShader** — WebGPU included. The `_atmosphere-globe-gate`
idiom is the template: before/after on one boot (DC > 0 proves the new pass painted),
backend asserted via `window.__xgisActiveBackend` so a silent fallback cannot green it,
self-referential pixel bounds rather than absolute constants.

```bash
cd playground && XGIS_SOFTWARE_GPU=1 HEADED=0 \
  XGIS_CHROMIUM_EXECUTABLE=$(ls -d /opt/pw-browsers/chromium_headless_shell-*/chrome-linux/headless_shell | head -1) \
  ./node_modules/.bin/playwright test <spec>          # WebGL2 page: ?forcegl2=1
```

Standing gates that must stay green in every phase, not only the phase that touches them:
`_coverage-black-ratio.spec.ts` (ADR-0007's ≤ 2 % black), `polygon-variant-diff.test.ts`
(ADR-0003 emit stability), `loc-ceiling-ratchet.test.ts`, `spec-coverage-drift.test.ts`.

## 9. Open questions for the owner

1. **Sun position.** `sky-atmosphere-sun` and `fog`'s `star-intensity` imply a sun/time-of-day
   the engine has no concept of; `_light` (`map.ts:901-905`) carries a position that is a
   _lighting_ rig, not an astronomical sun. Phase 3 can either reuse `_light`'s direction
   (cheap, slightly wrong) or take the sun as an explicit style-supplied vector (honest,
   one more host field). Recommendation: the explicit vector, defaulting to `_light`.
2. **`vertical-range`** (fog) is altitude-banded, which presumes terrain — ADR-0012 D5.
   Recommend warning it as out-of-scope until D5 lands, rather than approximating.
